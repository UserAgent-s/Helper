# ADR 0004: Один захват на устройство, раздача потребителям, весь системный звук по умолчанию

## Статус

Принято (2026-11-08). Частично заменяет ADR 0002: асинхронный Whisper в `answers` больше не используется.

## Контекст

- Захват жёстко привязан к одному приложению: `UserDefaultsPreferredAudioSourceStore.swift:6` по умолчанию даёт `com.google.Chrome`, а `ScreenCaptureKitSystemAudioCapturing.swift:43-48` падает с `targetApplicationNotFound`, если его нет.
- Владелец хочет весь системный звук плюс свой микрофон отдельным каналом (требования R1, R9, R12), а основная платформа звонков у него Google Meet в Chrome (R15).
- Каждый потребитель (Realtime, рекордер, уровни, позже веб-панель и канал «Я») сейчас читает аудио сам. `AsyncStream` не поддерживает multicast: `ModeCoordinator.stateUpdates()` (`ModeCoordinator.swift:31-33`) уже читают два вида, и каждое событие получает только один из них.
- CLAUDE.md требует: «answers mode never starts Whisper». ADR 0002 и `QuestionAnswerLogger.swift:57-61` при этом запускают WhisperKit в `answers` для журнала.

## Решение

1. На каждое физическое устройство один источник: один `SCStream` для системного звука и один движок для микрофона. Раздачу делает `CaptureHub` через `AsyncBroadcaster<Element>`. У каждого подписчика свой буфер и своя политика переполнения, поэтому медленный потребитель не задерживает Realtime.
2. `SystemAudioScope` по умолчанию `.wholeSystem`: `SCContentFilter(display:excludingApplications:exceptingWindows:)` со своим приложением в исключениях и `excludesCurrentProcessAudio = true`. Пресет «Только Google Chrome» — это `.application(bundleID, fallbackToWholeSystem: true)`, учитывающий helper-процессы. Пользователь может исключать приложения.
3. Основной backend — ScreenCaptureKit. Core Audio process tap (`CATapDescription`, macOS 14.2+) проверяется спайком за флагом разработчика. На него переходим, только если он лучше хотя бы по двум из пяти метрик (задержка, CPU, стабильность при смене устройства вывода, запросы разрешений, качество) и нигде не хуже.
4. Микрофон выбирается явно по UID устройства. Continuity (`ccwd`/`ccwl`), виртуальные и aggregate-устройства автоматически не выбираются, но их можно выбрать вручную. За системным устройством по умолчанию приложение не следует.
5. `OutputRoute` (наушники, динамики, Bluetooth, AirPlay) определяется через Core Audio и отслеживается с debounce. Это вход для эхо-политики канала «Я» (M3).
6. Канал «Я» включается в `answers` отдельной настройкой (M3). До этого `answers` микрофон не открывает.
7. Текст вопроса в `answers` берётся из транскрипции входа Realtime. WhisperKit в `answers` не запускается (S1.7).

## Альтернативы

- Сразу перейти на process tap. Отвергнуто: SCK уже работает, разрешение выдано, и в M6 то же разрешение нужно для `SCScreenshotManager`.
- Отдельный захват под каждого потребителя. Отвергнуто: несколько `SCStream` дают рассинхрон и двойную нагрузку.

## Последствия

- Весь звук Mac, включая уведомления и музыку, уходит в OpenAI, пока активен `answers`. Об этом говорят onboarding, privacy.md и индикатор режима.
- Ложных автоответов станет больше. Калибровка VAD и список исключений входят в S1.6.
- Тест «answers never starts Whisper» становится обязательным.

## Критерии пересмотра

Изменения в захвате и раздаче правят этот ADR тем же коммитом. Пересмотр, если спайк CATap выигрывает по критериям пункта 3 или если SCK перестанет отдавать системный звук без запроса на запись экрана.

## Результат спайка CATap (S1.5)

Core Audio tap работает на macOS 27.2 и надёжно исключает собственный процесс, но сравнение с SCK по пяти метрикам в одинаковых условиях не сделано. Дефолт остаётся ScreenCaptureKit, tap доступен только за флагом разработчика. Таблица замеров — в `docs/implementation-status.md` (S1.5).

## Профили микрофона и Voice Processing (S3.1)

Микрофон запускается с профилем. `.me` (канал «Я») работает на 24 кГц, формат Realtime. `.recording` работает на 16 кГц, формат WhisperKit. Voice Processing (AEC macOS) включается только для `.me` и только при риске эха (динамики), с минимальным ducking других приложений. С наушниками AEC не нужен и лишь искажает голос. Recording оставлен без VPIO: его стенограмма уже разделяет источники, а VPIO меняет громкость звука других приложений во время записи. Смена маршрута вывода перезапускает микрофон через `CaptureHub`, подписчики сохраняются. При VPIO используется только канал 0 из 9 каналов входа, mixer движка не трогается: обращение к нему при VPIO ломает инициализацию.

## Текст «Я» и экрана как контекст, а не триггер (S3.2)

Реплики владельца и текст экрана попадают в основную Realtime-сессию как текстовые user-items с метками `[Я]:` и `[Экран: app]` и никогда не запускают ответ сами: `response.create` не отправляется, turn detection по системному звуку не меняется. Роль user, а не system, выбрана, чтобы модель видела реплики владельца как часть разговора в правильном порядке. Отвечать на них запрещает правило в инструкциях. Жизненный цикл такой же, как у остального контекста: удаление после завершённого ответа и по maxAge, никогда во время стрима. Domain знает только `InjectedContext`, а формат сообщений остаётся в адаптере провайдера.

## Отдельная транскрипция «Я» (S3.3)

Речь владельца распознаётся во второй WebSocket-сессии OpenAI с `intent=transcription` и `gpt-live-transcribe`, а не в основной. В основной сессии любой commit аудио может запустить ответ и смешать голоса. Транскрипционная сессия ответов не создаёт, turn detection в ней выключен, ход закрывает клиентский VAD. Сбой этой сессии изолирован: после исчерпания переподключений канал «Я» отключается со статусом `unavailable`, answers продолжает работать по системному звуку. Domain видит только `MeTranscribing`.

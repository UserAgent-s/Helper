# ADR 0006: Сессия ассистента — контейнер над режимами, а не четвёртый режим

## Статус

Принято (2026-11-08). Реализация в M4.

## Контекст

- Владелец хочет запускать и останавливать сессии и хранить их историю (R10).
- ADR 0001 закрепляет ровно три взаимоисключающих режима. `qa_entries` сейчас не связаны ни с какой сессией (`SQLiteMigrations.swift`, схема v1).

## Решение

1. `AssistantSession` с состояниями Start и Stop живёт над `ModeCoordinator`. Внутри одной сессии может быть несколько отрезков разных режимов (`session_spans`).
2. Хранение: `meetings.kind = session`, `session_spans`, `session_id` у `qa_entries`, стенограммы «Собеседник» и «Я», раскрытия, тексты экрана, закладки.
3. Пока сессия активна, в `answers` сохраняется полная стенограмма. Это меняет прежний пункт продуктового контракта «полный разговор не сохраняется» и включается только внутри сессии.
4. Срок хранения (`historyRetentionDays`) реально применяется: старые сессии удаляются вместе с аудио и FTS-строками.

## Альтернативы

- Четвёртый режим `session`. Отвергнуто: ломает инварианты ADR 0001 и тесты переходов.

## Последствия

- Миграция v2 с резервной копией до неё.
- Поиск по истории: FTS5 unicode61 плюс trigram (см. ADR 0008).

## Критерии пересмотра

Если понадобятся параллельные сессии или сессии на клиентском устройстве.

## Дополнение S4.1: схема

- «Миграция v2» из плана — это `schema_migrations.version = 4`: версии 1–3 уже заняты (базовая схема, модель расшифровки вопроса, сопряжённые устройства). Миграция идёт одной транзакцией `BEGIN IMMEDIATE`. До неё, внутри той же блокировки, `sqlite3_backup` из отдельного read-only соединения пишет копию `useragent057.sqlite3.pre-v4.bak`. Перед циклом миграций выполняется `wal_checkpoint(PASSIVE)`. Сам `sqlite3_backup` читает и WAL, так что копия консистентна и без чекпоинта.
- Сессия — это строка `meetings` с `kind = 'assistant'`. Старые записи получают `kind = 'recording'` и один span `legacy_<id>` с режимом `recording`. Все дочерние таблицы (`session_spans`, `screen_contexts`, `deep_expansions`, `bookmarks`, а также `qa_entries.session_id`) ссылаются на `meetings(id) ON DELETE CASCADE`. Каскад запускает FTS-триггеры, поэтому удаление сессии чистит и поисковые индексы. `qa_entries.screen_context_id` при удалении снимка экрана обнуляется (`SET NULL`).
- `utterances.speaker` хранит `Speaker.rawValue` (`me` и `them`). Бэкфилл переводит `source = 'local'` (микрофон, Whisper) в `me`, а остальное — в `them`. `origin` старых строк — `whisper_local`. `captured_at` считается как `meetings.started_at + started_ms` с точностью до секунды, в том же формате ISO8601, что и остальная база.
- У каждой текстовой таблицы два внешних FTS5-индекса (MEM-2): `<table>_fts` с `unicode61 remove_diacritics 2` и `<table>_trgm` с `trigram`. У `bookmarks` только словарный индекс: заметки короткие. Триграммы без `remove_diacritics`, потому что эта опция появилась в SQLite 3.45, а на macOS 14 системная 3.43.
- `unicode61` не приравнивает «ё» к «е» (проверено пробой). Поэтому триггеры и первичное заполнение пишут в индекс `replace(text, 'ё', 'е')`. Замена сохраняет длину в байтах, так что `snippet()` по контент-таблице не сдвигается. Встроенный `'rebuild'` для этих индексов использовать нельзя: он индексирует текст без замены, и последующие `'delete'` разойдутся с индексом. Перестраивать нужно через `'delete-all'` и `INSERT … SELECT` с той же заменой.
- `search_aliases(term, alias)` с `COLLATE NOCASE` засеяна несколькими парами RU и EN (Kafka/Кафка, Postgres, Kubernetes/k8s, Redis). Использует её `FTSQueryBuilder` в S4.7.

## Дополнение S4.4: запись в сессию

- Всё, что пишется при активной сессии, получает её id. `QuestionAnswerLogger` читает `activeSessionID` один раз в `beginDraft` и хранит его в `QuestionAnswerPair.sessionID`; поздние обновления черновика не меняют привязку (`ON CONFLICT … session_id = COALESCE(старый, новый)`).
- Стенограмму `answers` пишет `SessionRecorder` из `AnswersModeController.transcriptEvents`: только финальные события, `them` с `origin = realtime_input`, `me` с `origin = me_channel`, `captured_at` — время получения финала. Повтор финала того же item не пишется.
- `recording` не превращает Whisper-сегменты в `TranscriptEvent`: контроллер пишет их сам в строку сессии. Так перевод (S6.1), который подписан на `TranscriptEvent`, не увидит данные `recording` (снят риск из ревью плана v3).
- Сессию для `recording` контроллер берёт через `SessionContextProviding.sessionForCapture(mode:)`. Если сессии нет, координатор создаёт её сразу (а не после смены фазы режима), иначе запись создала бы свою встречу, а сверка режима — вторую. Создание дедуплицируется общей задачей. Без координатора контроллер, как раньше, создаёт свою встречу.
- Пустая сессия (без реплик, Q&A, закладок, снимков экрана, раскрытий и без отрезка `recording`) удаляется при завершении. Перед проверкой координатор ждёт сброса очередей записи (`beforeFinalize`). Сессии с отрезком `recording` не удаляются, потому что у них может быть WAV на диске.

## Дополнение S4.5: управление сессией

- Старт, стоп и звезда одинаково доступны из веб-панели (`session.start|stop|resume`, `star_last`, `mark_moment`), из меню строки состояния и по глобальным хоткеям ⌃⌥⌘S и ⌃⌥⌘B. Все три пути идут в `SessionControlling`.
- Повторный старт при активной сессии ничего не меняет: мост и `SessionControlViewModel` проверяют `currentState` до вызова `start()`. Стоп без сессии тоже ничего не делает.
- Пока сессия не завершена, Mac не засыпает (`ModeActivityGuard.observeSessions`), в том числе в пассивном режиме между отрезками.
- Клиенты получают события из потока `SessionEvent`: `session.started` (с `resumed`), `session.stopped` (с `reason`), `bookmark.added` и `bookmark.removed`. Удаление пустой сессии (`.discarded`) на провод не уходит.


## Дополнение S4.6: финализация и экспорт

- Сразу после Stop у сессии есть заголовок: `SessionCoordinator(afterFinish:)` вызывает `SessionFinalizer.finalize` до события `.stopped`. Эвристика полностью локальная («ДД.ММ · первый вопрос» или «Звонок ЧЧ:ММ») и не перезаписывает заголовок пользователя.
- Саммари после Stop только по opt-in (`autoSummaryOnStop`, по умолчанию выключено). Без него при финализации нет ни сетевых вызовов, ни файлов. Ошибка саммари не меняет статус сессии.
- Экспорт в Markdown делается не на Mac, а в браузер второго устройства. Веб запрашивает `export.request`, хаб выдаёт одноразовый тикет на 120 с, привязанный к сессии и устройству, и браузер скачивает `GET /export/{sid}.md?t=…`. Документ рендерится при выдаче тикета, тикет сгорает при первой попытке. Ручной экспорт встречи в `~/Documents/UserAgent057/Exports` из S2.9 остаётся отдельной функцией и по-прежнему выключен по умолчанию.
- Разделы документа идут в фиксированном порядке: заголовок, саммари, отмеченное, Q&A с раскрытиями, транскрипт с подписями «Я» и «Собеседник» и переводом, тексты экрана.

## Дополнение S4.7: поиск

- Пользовательский ввод не передаётся в FTS5 как есть. `FTSQueryBuilder` режет ввод на токены и заключает каждый в кавычки. Операторы FTS5 становятся обычными словами, а термы соединяются через AND. Словарный индекс ищет по префиксу (`"tok"*`), триграммный — по подстроке. Алиасы из `search_aliases` раскрываются одним шагом через OR.
- Поиск по сессиям объединяет все FTS-индексы одним `UNION ALL`. Словарные совпадения ранжируются выше триграммных, внутри — по `bm25`. Результат группируется по сессии, сниппет выделяется «…».

## Дополнение S4.8: история

- `SessionHistoryQuerying` (Domain) — единственный путь чтения истории для веба и для вкладки «Сессии» на Mac. Список строится только из заголовков (`SessionRepository.headers`) с курсором `startedAtMs_uuid`. Карточка строится из `detail` и группирует раскрытия под их Q&A; раскрытия без Q&A показываются отдельно.
- Провод: `history.list {cursor?, q?, limit?}` возвращает `history.page`, `history.get {sessionId}` возвращает `history.session`. Оба ответа персональные и не попадают в буфер повтора. Если задан `q`, работает поиск из S4.7: страница без курсора, у элементов есть `hits` и нет счётчиков.
- Карточка, которая не помещается в кадр 1 МБ, сохраняет самый длинный влезающий префикс транскрипта и флаг `truncated`. Полный текст остаётся в экспорте `.md`.
- Удалять историю из веба нельзя (v1).

## Дополнение S4.9: срок хранения

- `RetentionPolicy(days, keepScreenTexts)` и `RetentionScheduler` (Domain) запускают очистку при старте, раз в 24 часа и при изменении настройки. Политика без срока и с сохранением текстов экрана ничего не делает и не трогает базу.
- `RetentionSweeper` удаляет в одной транзакции завершённые сессии, у которых `COALESCE(last_activity_at, ended_at, started_at)` раньше границы, кроме `pinned = 1` и текущей сессии координатора. Удаление каскадное и чистит все FTS-индексы через триггеры. Q&A по возрасту удаляются только без `session_id`: Q&A закреплённой сессии раньше удалялись по `asked_at`, теперь живут вместе с сессией.
- Соединение работает с `secure_delete = ON`.

# ADR 0002: Прямой аудио-поток в Realtime API, без STT в критическом пути

## Статус

Принято.

## Контекст

Естественная на первый взгляд архитектура — сначала локально распознать речь (Whisper/STT), затем отправить текст вопроса в LLM. Это добавляет полный проход локального распознавания (сотни миллисекунд — секунды на Apple Silicon для не самых коротких фраз) до того, как модель вообще начинает генерировать ответ. Приоритет режима `answers` — минимальная задержка от конца речи до первого видимого токена ответа.

## Решение

`answers` передаёт PCM16 24kHz mono аудио напрямую в OpenAI Realtime API по мере поступления (`input_audio_buffer.append`), без промежуточного локального STT. Модель `gpt-realtime-2.1` с `reasoning.effort: low` и text-only выводом сама выполняет распознавание речи внутри Realtime-сессии и решает, готова ли она ответить (обычный `response.create` от серверного VAD) или должна вернуть скрытый `⟦WAIT_FOR_QUESTION⟧`.

Локальный Whisper запускается **только асинхронно, после** того как видимый ответ уже начал выводиться, и только для ограниченного окна «контекст + вопрос», нужного исключительно для журнала Q&A. Он никогда не блокирует и не задерживает генерацию или отображение ответа.

## Последствия

- `speech_end_to_first_delta_ms` не включает время локального распознавания.
- WhisperKit runtime в режиме `answers` — best-effort фоновая задача; её отмена/сбой не должны влиять на уже показанный ответ.
- Требуется устойчивый to WebSocket-адаптер (`RealtimeAnswerClient`) с явной обработкой обрыва соединения, т.к. он находится в критическом пути UX.
- Домен обязан типизировать формат аудио (`PCMAudioFrame`) независимо от `ScreenCaptureKit`, чтобы конвертация в 24kHz PCM16 была тестируема без реального захвата экрана.

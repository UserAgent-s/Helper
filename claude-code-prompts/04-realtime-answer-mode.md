# Этап 04. Режим быстрых ответов через OpenAI Realtime

## Цель

Реализуй минимальный по задержке путь `системное аудио → OpenAI Realtime → потоковый текст`. Локальное или облачное speech-to-text не должно предшествовать генерации ответа.

## Протокол

1. Создай типизированный `RealtimeClient` поверх `URLSessionWebSocketTask` или другого нативного WebSocket-клиента без тяжёлой сетевой обвязки.
2. Используй актуальный GA endpoint и модель `gpt-realtime-2.1`.
3. Не используй `OpenAI-Beta: realtime=v1` и legacy event schema.
4. Источник ключа — только `SecretStoring`; не читай секрет из исходников, plist или логируемых environment values.
5. Открывай соединение при запуске `answers` и держи его прогретым только до выхода из режима.
6. Поток аудио — 24 kHz mono PCM16. Отправляй небольшие последовательные chunks без ожидания окончания вопроса.
7. Настрой сессию на текстовый вывод без аудио:
   - `type: realtime`;
   - `model: gpt-realtime-2.1`;
   - `output_modalities: ["text"]`;
   - `reasoning.effort: low`;
   - `server_vad`;
   - начальные значения `threshold: 0.5`, `prefix_padding_ms: 300`, `silence_duration_ms: 300`;
   - автоматическое создание ответа и прерывание устаревшего ответа при новой речи.
8. Вынеси VAD-параметры в настройки разработчика, но используй безопасные значения по умолчанию.
9. Слушай и типизированно декодируй как минимум:
   - session lifecycle/error events;
   - `input_audio_buffer.speech_started`;
   - `input_audio_buffer.speech_stopped`;
   - conversation item lifecycle events, необходимые для подтверждения committed input и последующей адресной очистки;
   - `response.created`;
   - `response.output_text.delta`;
   - `response.output_text.done`;
   - `response.done`;
   - rate-limit и usage события, если они приходят.
10. Не жди финальной транскрипции входа. Не запускай Whisper до получения/отрисовки ответа.
11. Автоматический response после речевого хода без вопроса должен быть скрытым классифицирующим ходом: удали только его output item, но сохрани соответствующие user audio items как контекст следующего вопроса.

## Инструкция Realtime-модели

Используй следующую системную инструкцию как версионируемую константу приложения. Сохрани короткие именованные разделы: это исполняемый контракт поведения, а не пример текста.

```text
# Роль и цель
Ты помогаешь пользователю отвечать на вопросы во время рабочего разговора. Формулируй ответ так, как отвечал бы сильный senior software engineer на собеседовании: уверенно, технически точно, с учётом production-реальности и без хвастовства.

# Контекст и момент ответа
- Считай всю содержательную речь после предыдущего показанного ответа накопительным контекстом следующего вопроса. Контекст может включать несколько законченных утверждений, объяснение задачи и паузы между речевыми ходами.
- Никогда не отбрасывай предыдущие контекстные ходы только потому, что в них ещё не было вопроса.
- Каждый вопрос в этом режиме предназначен пользователю. Не определяй адресата вопроса и не отказывайся отвечать из-за имени, обращения или других участников разговора.
- Вопросы, процитированные внутри условия задачи, примеры, риторические вопросы и вопросы, на которые говорящий сразу отвечает сам, являются контекстом, а не сигналом к ответу.
- Когда в накопленном контексте появился явный вопрос либо однозначная просьба предложить решение, ответь с учётом всего контекста после предыдущего ответа.
- Если неясно, завершил ли говорящий постановку финального вопроса, предпочти ⟦WAIT_FOR_QUESTION⟧: пользователь при необходимости вызовет `FORCE_ANSWER_NOW`.
- Если вопрос ещё не прозвучал, верни ровно ⟦WAIT_FOR_QUESTION⟧ и ничего больше.
- Если response-scoped инструкция содержит `FORCE_ANSWER_NOW`, пользователь подтверждает, что вопрос уже задан. Сразу ответь по наиболее вероятному последнему вопросу из накопленного контекста и никогда не возвращай ⟦WAIT_FOR_QUESTION⟧. Если формулировка неполна, сделай одно коротко обозначенное допущение.

# Язык
- Определи основной естественный язык именно текущего вопроса и напиши весь ответ только на этом языке.
- Названия технологий, идентификаторы, команды и фрагменты кода на другом языке не меняют язык вопроса. Например, русский вопрос про Kubernetes требует русского ответа.
- Если вопрос действительно смешанный, используй язык его основной смысловой части. Не переводи ответ и не повторяй его на втором языке.

# Качество ответа
- Начни первое предложение с прямого ответа или решения.
- Для вопросов «почему», «как спроектировать», «что выбрать» и сравнений дай краткое обоснование и назови один существенный trade-off; альтернативу или edge case добавляй только когда они влияют на решение.
- Для диагностики укажи наиболее вероятную причину, способ проверки и безопасное production-действие, если вопрос этого требует.
- Для вопросов о коде опиши надёжный production-подход. Упоминай сложность, конкурентность, производительность, безопасность и отказоустойчивость только когда они релевантны; код пиши только если его явно попросили.
- Не выдумывай факты, API, цифры, личный опыт или контекст пользователя. Если важных данных не хватает, кратко обозначь одно допущение и дай безопасный ответ при этом допущении.

# Формат
- Верни только готовый ответ кандидата: без приветствия, пересказа вопроса, скрытых рассуждений, оценок вопроса и служебных фраз.
- Обычно используй 2–4 коротких предложения и не более 120 слов. Не создавай список, если вопрос явно не требует перечисления.
- Когда уместно, говори естественно от первого лица, например «Я бы…», но не заявляй о несуществующем опыте.
```

Первые входящие символы временно проверяй на sentinel `⟦WAIT_FOR_QUESTION⟧`. Sentinel не должен появляться в UI или журнале. После того как поток однозначно не является sentinel, немедленно публикуй уже полученные символы и все последующие delta.

## Контекст и очистка

1. Не накапливай весь митинг в серверной Conversation.
2. Начинай новый `AnswerContextWindow` после предыдущего видимого ответа. Сохраняй ID всех committed user audio items этого окна через несколько речевых ходов.
3. Если response равен `⟦WAIT_FOR_QUESTION⟧`, удали только assistant output items этого response. User audio items и соответствующий ограниченный локальный ring-buffer остаются контекстом.
4. При первом валидном delta заморозь набор context item IDs для текущего ответа. После `response.done` и создания локального снимка для Q&A-журнала адресно удали накопленные input/output items и начни пустое окно следующего вопроса.
5. Ограничь локальное окно по времени и памяти, например пятью минутами и 32 MiB по умолчанию. При вытеснении удаляй только самые старые законченные контекстные ходы, считай метрику и показывай неконтентный diagnostic warning; никогда не пиши это аудио на диск.
6. При новой речи во время видимого незавершённого ответа отменяй его, очищай overlay и начинай новое окно контекста. Обычная новая речь во время `collectingContext` продолжает текущее окно и ничего не очищает.

## Действие «Ответить сейчас»

1. Добавь в доменный API идемпотентный `forceAnswerNow()`/`AnswerTriggering`, доступный только в активном `answers`.
2. Кнопка означает, что вопрос уже задан, но автоматический ход ошибочно вернул/готовит `⟦WAIT_FOR_QUESTION⟧`. Она не является push-to-talk и не запускает транскрипцию.
3. Если уже идёт видимый валидный ответ, не создавай второй response. Если идёт ещё невидимый автоматический response, отмени его, пометь его ID устаревшим и после подтверждения cancellation создай один manual response.
4. Если последний речевой ход ещё активен или committed input item ещё не подтверждён, установи ровно один `manualResponsePending` и отправь запрос сразу после `speech_stopped`/подтверждения item. Не создавай параллельные запросы от повторных кликов.
5. Если накопленного committed-контекста нет, не вызывай API и верни UI-состояние `noContext`.
6. Отправь обычный `response.create` в default conversation, чтобы модель увидела все накопленные items. Укажи `output_modalities: ["text"]`, metadata с trigger/correlation ID и response-scoped инструкцию:

```text
FORCE_ANSWER_NOW. Пользователь подтверждает, что вопрос уже был задан. Используй весь накопленный контекст после предыдущего показанного ответа и ответь сейчас. Не возвращай ⟦WAIT_FOR_QUESTION⟧. Соблюдай системные правила языка, senior-level качества, достоверности и краткости.
```

7. Не добавляй перед manual `response.create` STT, классификатор или другой модельный запрос. GA Realtime adapter должен отдельно типизировать manual response event и проверять схему по официальному руководству `https://developers.openai.com/api/docs/guides/realtime-conversations`.
8. Первый валидный ответ — автоматический или ручной — атомарно выигрывает turn. Все поздние события проигравшего response ID игнорируются, context window очищается только один раз.

## Надёжность

- Реализуй timeout, cancellation и ограниченный reconnect с jitter.
- Не повторяй автоматически уже завершённый вопрос после reconnect.
- При потере сети покажи состояние, останови отправку и не накапливай бесконечный аудиобуфер.
- Ошибка авторизации переводит приложение в `passive` и открывает настройки ключа.
- Никогда не логируй Authorization header, base64 audio или содержимое полного server event без редактирования.

## Метрики

Собирай monotonic timestamps:

- первый отправленный audio frame;
- `speech_started`;
- `speech_stopped`;
- response created;
- первый text delta;
- first paint в overlay;
- response done.
- manual trigger pressed;
- manual `response.created` и первый manual text delta;
- длительность накопленного контекста и trigger kind `automatic`/`manual`.

## Тесты

Создай fake WebSocket transport и проверь:

- порядок session update и audio append;
- публикацию первого delta до `response.done`;
- подавление sentinel и сохранение user input items после `⟦WAIT_FOR_QUESTION⟧`;
- несколько контекстных ходов перед вопросом используются одним валидным ответом;
- `forceAnswerNow()` отправляет ровно один `response.create` с default conversation context и response-scoped инструкцией;
- повторные клики, pending commit и гонка с автоматическим response не создают двойной видимый ответ;
- отсутствие API-вызова manual trigger при пустом контексте и его отмену при выходе из режима;
- отмену предыдущего ответа новой речью;
- очистку контекста;
- reconnect и отсутствие двойного ответа;
- редактирование чувствительных логов;
- отсутствие вызовов `LocalTranscribing` на критическом пути.
- передачу полной системной инструкции в session update без сокращения языкового и senior-quality контракта;
- сохранение Unicode и исходного языка потокового ответа в overlay и Q&A-журнале без клиентского перевода.

## Критерии приёмки

- Аудио начинает уходить во время произнесения вопроса.
- Объяснение задачи через несколько речевых ходов сохраняется до последующего вопроса и не отображается как ответ.
- Первый видимый текст формируется по delta, а не после done.
- Whisper не вызывается для получения ответа.
- Ответ полностью соответствует языку вопроса; русские вопросы с английскими техническими терминами не переключают ответ на английский.
- Ответ начинается с сути и соответствует краткому senior-level формату, заданному системной инструкцией.
- `Ответить сейчас` начинает потоковый ответ по уже накопленному контексту без предварительной транскрипции.
- Полный митинг не накапливается в Realtime history.
- Выход из режима гарантированно отменяет WebSocket и очищает память.

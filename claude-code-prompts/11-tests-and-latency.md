# Этап 11. Тестирование, измерение задержки и отказоустойчивость

## Цель

Создай доказательную тестовую систему, которая подтверждает главные продуктовые свойства, особенно отсутствие транскрипции в критическом пути быстрых ответов.

## Unit tests

Покрой:

- ModeCoordinator и все переходы;
- отмену/очистку ресурсов;
- аудиоформаты, ring buffer и backpressure;
- Realtime event decoder;
- streaming reducer overlay;
- sentinel filtering;
- накопление нескольких Realtime input items до вопроса;
- идемпотентный manual answer trigger и арбитраж manual/automatic response;
- Q&A draft lifecycle;
- асинхронную транскрипцию только вопроса;
- chunk overlap/deduplication recording mode;
- SQLite migrations/repositories/FTS;
- summary schema и export;
- Keychain/redaction abstractions.

Отдельно проверь, что versioned-константа системной инструкции целиком отправляется при конфигурации Realtime-сессии и содержит контракт языка, senior-quality, накопительного контекста, manual force, длины и sentinel. Клиент не должен переводить, переписывать или ждать определения языка перед отправкой аудио.

## Integration tests

1. Создай scripted fake Realtime transport, который принимает аудиофреймы и выдаёт события с управляемыми задержками.
2. Докажи тестом, что `response.output_text.delta` попадает в overlay до `response.done`.
3. Внедри spy `LocalTranscribing` и докажи, что до первого видимого delta у него ноль вызовов.
4. После валидного ответа докажи один вызов транскрипции ограниченного окна «контекст + вопрос».
5. После sentinel докажи ноль записей/транскрипций, сохранение committed user item и включение этого контекста в следующий ответ.
6. После нескольких контекстных ходов и вопроса докажи один видимый ответ, затем адресную очистку всех items окна.
7. После `Ответить сейчас` докажи ровно один `response.create`, trigger metadata, response-scoped `FORCE_ANSWER_NOW`, отсутствие STT перед первым delta и обычное Q&A-логирование.
8. Проверь повторные клики, клик во время незавершённой речи, клик при пустом контексте, гонку с автоматическим response и выход из режима при pending manual trigger.
9. В `recording` внедри network spy и докажи ноль запросов.
10. В `passive` докажи отсутствие capture, transcription, network и content writes.

## Audio fixtures

Добавь небольшие легально созданные тестовые WAV/PCM fixtures либо генерируй их в тестах. Не добавляй записи реальных встреч. Нужны сценарии:

- короткий вопрос;
- утверждение без вопроса;
- объяснение задачи в трёх речевых ходах, затем вопрос;
- условие с процитированным/риторическим вопросом, продолжение объяснения и только затем финальный вопрос;
- вопрос, ошибочно классифицированный fake transport как ожидание, затем manual trigger;
- пауза внутри вопроса;
- два вопроса подряд;
- русский;
- английский;
- фоновой шум;
- смена источника/обрыв потока.

## Language and answer-quality evals

Добавь репрезентативный набор вопросов без реальных данных встреч. Для каждого сценария храни входной текст/аудио, ожидаемый язык ответа и рубрику, но не фиксируй единственный дословный ответ:

- вопрос полностью на русском;
- вопрос полностью на английском;
- русский вопрос с терминами `event loop`, `backpressure`, `Kubernetes` и фрагментом кода;
- английский вопрос с русским именем или короткой цитатой;
- действительно смешанный вопрос с явно определённой основной смысловой частью;
- design/comparison-вопрос, где нужен существенный trade-off;
- debugging-вопрос, где нужны гипотеза, проверка и безопасное действие;
- вопрос с недостающим контекстом, где нельзя выдумывать факты;
- утверждение без вопроса, ожидающее sentinel и сохранение как контекст следующего вопроса.

Рубрика для валидного ответа:

1. `language_match` — весь обычный текст ответа на ожидаемом языке; общепринятые технические термины, идентификаторы и код разрешены. Несовпадение является hard failure.
2. `directness` — первое предложение сразу отвечает по существу.
3. `technical_correctness` — нет фактических ошибок и выдуманных API/поведения.
4. `senior_judgment` — есть релевантное обоснование и существенный trade-off/edge case, когда вопрос этого требует, без энциклопедического перечисления.
5. `production_mindset` — при необходимости учтены эксплуатация, конкурентность, безопасность, производительность или отказоустойчивость.
6. `brevity` — не более 120 слов и обычно 2–4 коротких предложения.

Offline CI обязан проверять доставку prompt, Unicode streaming, отсутствие клиентского перевода и scripted fake-ответы. Реальные model evals запускай отдельной opt-in командой только при наличии ключа; оценивай язык детерминированно, а качество — rubric-based evaluator плюс ручная выборочная проверка. Никогда не включай сетевой eval в обязательный build без явного opt-in.

## Latency harness

Создай debug-инструмент и локальный отчёт, измеряющий:

- capture callback → WebSocket send;
- speech stopped → first delta;
- first delta → first paint;
- полный response time;
- reconnect time;
- manual trigger → first delta;
- длительность context window и число удержанных/вытесненных контекстных ходов;
- остановку режима;
- очередь и dropped frames.

Требования:

- используй monotonic clock;
- отделяй сетевую/модельную задержку от UI;
- считай count, p50, p95, max;
- не сохраняй содержание аудио/текста в latency report;
- `first_delta_to_first_paint_ms` не должен содержать искусственный debounce и должен быть близок к одному display frame в локальном fake-тесте.

## Failure injection

Проверь:

- отказ разрешения;
- неверный API-ключ;
- network loss;
- malformed event;
- rate limit;
- Whisper load failure;
- disk full/SQLite error;
- sleep/wake;
- приложение meeting исчезло;
- переключение режима во время активного ответа/чанка.

Каждый сценарий обязан либо восстановиться, либо перейти в `passive` без утечки ресурсов и ложного индикатора активности.

## Проверки проекта

Запусти форматирование/линтинг, build и все тесты. Если проект использует конкретный formatter/linter, следуй его конфигурации; не вводи новый инструмент без необходимости.

## Критерии приёмки

- Тестом доказан прямой audio-to-Realtime critical path.
- Тестом доказан streaming UI до done.
- Тестом доказано накопление контекста через несколько ходов, ручной запуск без STT и отсутствие двойного ответа.
- Тестом доказан нулевой network в recording и нулевая обработка в passive.
- Русские, английские и смешанные сценарии подтверждают совпадение языка; технические термины не вызывают ложного переключения.
- Senior-quality rubric покрывает прямоту, техническую корректность, инженерное суждение и краткость.
- Отчёт задержки не содержит пользовательский контент.
- Все тесты проходят либо каждый внешний blocker документирован с командой воспроизведения.

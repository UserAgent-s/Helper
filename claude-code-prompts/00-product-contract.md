# Этап 00. Продуктовый контракт и архитектурные решения

## Цель

Прежде чем писать функциональный код, зафиксируй проверяемый контракт продукта и архитектуру, исключающую смешивание трёх режимов.

## Обязательные действия

1. Изучи репозиторий, `CLAUDE.md`, состояние git, существующий проект и зависимости.
2. Создай или обнови:
   - `docs/product-contract.md`;
   - `docs/architecture.md`;
   - `docs/implementation-status.md`;
   - `docs/adr/0001-three-exclusive-modes.md`;
   - `docs/adr/0002-direct-audio-realtime-critical-path.md`;
   - `docs/adr/0003-local-only-meeting-transcription.md`.
3. Зафиксируй enum режимов: `passive`, `answers`, `recording`.
4. Зафиксируй, что одновременно активен ровно один режим.
5. Опиши источники аудио:
   - `answers`: только системный звук выбранного приложения по умолчанию;
   - `recording`: системный звук плюс локальный микрофон;
   - `passive`: ни одного источника.
6. Опиши критический путь режима ответов:
   `ScreenCaptureKit → преобразование в PCM16 24 kHz → Realtime WebSocket → response.output_text.delta → NSPanel`.
7. Явно исключи локальный Whisper из критического пути режима ответов.
8. Опиши накопление контекста в `answers`:
   несколько входных речевых ходов и пауз → скрытый `⟦WAIT_FOR_QUESTION⟧` на ходах без вопроса → сохранение входных Realtime items → автоматический либо ручной ответ → очистка накопленного контекста.
9. Зафиксируй, что каждый вопрос в `answers` предназначен пользователю. Определение адресата не выполняется; всё содержимое до вопроса может быть объяснением задачи.
10. Опиши путь журнала вопросов:
   ограниченное in-memory окно «контекст + вопрос» → видимый ответ уже начат → асинхронный локальный Whisper → запись пары Q&A.
11. Опиши режим записи:
   аудио → локальный VAD/чанкинг → WhisperKit → финальные реплики → SQLite/FTS5.
12. Зафиксируй контракт ответа в `answers`:
    - ответ целиком использует основной естественный язык текущего вопроса;
    - технические термины и фрагменты кода на другом языке не считаются сменой языка;
    - действительно смешанный вопрос получает ответ на языке основной смысловой части;
    - качество соответствует сильному senior software engineer на собеседовании: прямой тезис, точное обоснование и только релевантные trade-offs/edge cases;
    - обычно 2–4 коротких предложения и не более 120 слов, чтобы качество не ломало latency-цель.
13. Зафиксируй действие `Ответить сейчас` внутри режима `answers`, а не как отдельный режим:
    - кнопка и глобальная горячая клавиша доступны, даже если текстовый overlay ещё не открылся;
    - действие использует уже накопленные Realtime conversation items и вызывает ровно один текстовый `response.create` с response-scoped инструкцией принудительного ответа;
    - никакой STT или второй модельный запрос не предшествует этому `response.create`;
    - гонка с автоматическим ответом разрешается идемпотентно: первый валидный ответ побеждает, поздний response игнорируется/отменяется.
14. Опиши безопасный переход: остановить старый режим полностью, дождаться освобождения ресурсов, затем запускать новый.
15. Зафиксируй политику данных:
    - приложение стартует в `passive`;
    - исходное аудио не хранится по умолчанию;
    - в `answers` не хранится полный разговор;
    - в `recording` не вызывается API распознавания или ответов;
    - саммари запускается пользователем после записи.
16. Зафиксируй целевые метрики:
    - `speech_end_to_first_delta_ms`;
    - `first_delta_to_first_paint_ms`;
    - `response_total_ms`;
    - `mode_stop_ms`;
    - `manual_trigger_to_first_delta_ms`;
    - `context_duration_ms` и trigger kind `automatic`/`manual`;
    - число потерянных/дублированных аудиофреймов.

## Архитектурные границы

Определи протоколы, которые позже будут реализованы конкретными сервисами:

- `ModeControlling`;
- `SystemAudioCapturing`;
- `MicrophoneCapturing`;
- `RealtimeAnswering`;
- `AnswerTriggering`;
- `LocalTranscribing`;
- `MeetingRepository`;
- `QuestionAnswerRepository`;
- `SummaryGenerating`;
- `SecretStoring`;
- `LatencyRecording`.

Системные фреймворки не должны попадать в доменные типы. Аудиоформат, временные метки, идентификаторы сегментов и события ответа опиши собственными `Sendable`-типами.

## Критерии приёмки

- Документация однозначно описывает три режима без четвёртого фонового режима.
- В диаграмме последовательности `answers` нет шага speech-to-text перед запросом ответа.
- Диаграмма показывает сохранение нескольких контекстных ходов до вопроса и отдельный путь `Ответить сейчас → response.create → text delta`.
- Контракт фиксирует совпадение языка вопроса и ответа и senior-уровень содержания без конфликта с ограничением длины.
- Для каждого ресурса указано, кто запускает и кто гарантированно останавливает его.
- Описана безопасная деградация в `passive` при любой ошибке.
- Внутренние состояния ожидания/ручного запуска не представлены как четвёртый режим приложения.
- В `docs/implementation-status.md` записаны проведённые проверки и принятые решения.

# Этап 02. Машина состояний трёх режимов

## Цель

Реализуй строгую, потокобезопасную и тестируемую машину состояний, которая никогда не оставляет активные ресурсы предыдущего режима.

## Модель

Используй доменные типы:

- `AppMode`: `passive`, `answers`, `recording`;
- `ModePhase`: `idle`, `starting`, `active`, `stopping`, `failed`;
- `ModeState`: текущий режим, фаза, время начала, необязательная пользовательская ошибка;
- `ModeTransition`: источник, цель, причина и correlation ID.

`ModeCoordinator` реализуй как actor. Все переходы проходят только через него.

Внутри `AnswersModeController` используй отдельный, не являющийся режимом приложения, `AnswerTurnPhase`: `collectingContext`, `automaticResponsePending`, `manualResponsePending`, `streaming`, `completed`. Он нужен для идемпотентного действия `Ответить сейчас`, но не добавляется в `AppMode`.

## Правила переходов

1. Повторный запрос уже активного режима идемпотентен.
2. Для перехода `A → B` сначала полностью выполни `stop(A)`, затем `start(B)`.
3. Если `stop(A)` не завершился корректно, выполни принудительное освобождение ресурсов и перейди в `passive`.
4. Если `start(B)` завершился ошибкой, освободи частично созданные ресурсы и перейди в `passive`.
5. Конкурирующие запросы переключения сериализуются; более новый запрос не должен оставлять промежуточный режим активным.
6. При завершении приложения всегда выполняется переход в `passive` с ограниченным таймаутом и безопасной отменой задач.
7. Выход из `recording` сначала финализирует текущие текстовые сегменты и встречу, затем освобождает ресурсы.
8. Выход из `answers` отменяет текущий ответ, закрывает Realtime-соединение, очищает in-memory аудиобуферы и скрывает overlay.
9. `passive` не создаёт пользовательских записей в базе и не запускает фоновые prewarm-задачи.
10. Переход из `answers` отменяет отложенный manual trigger и не позволяет ему отправить `response.create` после остановки режима.

## Интерфейсы жизненного цикла

Создай отдельные контроллеры `AnswersModeController` и `RecordingModeController`, реализующие общий протокол с асинхронными `start()` и `stop()`. Контроллеры должны быть внедрены в coordinator, а не создаваться внутри него.

Добавь `ResourceLease` или эквивалентный механизм, который делает владельца каждого ресурса явным и гарантирует одноразовый release.

## UI

Экран и menu bar должны показывать:

- активный режим;
- переходное состояние;
- ошибку разрешений или сети;
- подтверждение, что приложение вернулось в `passive`.

Не разрешай пользователю запустить второй режим параллельно. При переключении UI показывает переход, но остаётся отзывчивым.

## Тесты

Покрой как минимум:

- все шесть направленных переходов между разными режимами;
- идемпотентный повтор режима;
- ошибку старта каждого контроллера;
- ошибку остановки;
- два конкурентных переключения;
- завершение приложения во время `starting`;
- доказательство, что `start(B)` вызывается только после завершения `stop(A)`;
- отсутствие активных mock-ресурсов в `passive`.
- гонку manual trigger с автоматическим ответом: создаётся ровно один видимый ответ;
- отмену `manualResponsePending` при любом выходе из `answers`.

## Критерии приёмки

- Все переходы проходят через один actor.
- Невозможно одновременно активировать `answers` и `recording`.
- Любая ошибка возвращает безопасный `passive`.
- Тесты проверяют порядок вызовов, а не только итоговое значение enum.
- Нет detached-задач без владельца и явной отмены.

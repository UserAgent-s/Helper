# Этап 10. Настройки, секреты, разрешения и приватность

## Цель

Сделай поведение приложения прозрачным, безопасным и пригодным как для личной сборки, так и для будущего распространения.

## Настройки

Добавь типизированное хранилище настроек и UI для:

- выбранного источника системного звука;
- read-only индикатора автоматически определённого языка последнего вопроса в developer section; ручного переключателя языка ответа быть не должно, потому что ответ всегда обязан совпадать с языком текущего вопроса;
- позиции, opacity и размера overlay;
- времени автоскрытия ответа;
- VAD threshold/prefix/silence duration в developer section;
- локальной Whisper-модели;
- модели саммари;
- хранения аудио, выключенного по умолчанию;
- горячих клавиш, включая отдельное действие `Ответить сейчас` (по умолчанию `⌥Return`);
- периода хранения истории либо ручного удаления.

Изменение настройки, влияющей на активный pipeline, применяй безопасно: либо к следующему turn, либо через контролируемый restart текущего режима. Не перестраивай capture внутри callback.

## API-ключ

1. Реализуй Keychain service с add/update/read/delete.
2. Никогда не сохраняй ключ в UserDefaults, SQLite, plist, source code или diagnostic export.
3. Маскируй ключ в UI и не позволяй копировать его через обычный лог.
4. Добавь проверку формата без отправки; фактическую проверку авторизации делай только при запуске API-функции.
5. Для личной сборки разрешён пользовательский ключ в Keychain.
6. Создай протокол `RealtimeCredentialProviding`, чтобы позже заменить direct-key flow на PHP token broker без изменения аудио/режимов.
7. Документируй production-вариант: стандартный OpenAI key хранится на сервере, клиент аутентифицируется у приложения и получает краткоживущие credentials. Не реализуй небезопасный общий ключ внутри .app.

## Приватность

- Перед первым захватом покажи onboarding: что захватывается в каждом режиме и что сохраняется.
- `passive` визуально и технически означает отсутствие захвата.
- `answers` отправляет системный звук в API; пользователь должен видеть активный индикатор.
- `recording` обрабатывает аудио локально; пользователь должен видеть индикатор записи текста.
- Напомни пользователю получить согласие участников в соответствии с применимыми правилами.
- Не отправляй телеметрию содержимого разговоров.
- Diagnostic export должен включать версии, статусы и числовые метрики, но не аудио, transcript, ответы или секреты без отдельного явного opt-in.

## Логи

Используй privacy-aware logging:

- не логируй PCM/base64;
- не логируй полный Realtime event payload;
- не логируй prompt с пользовательским текстом;
- идентификаторы редактируй или хешируй, если они не нужны для локальной диагностики;
- ошибки API сохраняй без Authorization headers и user content.

## Разрешения

Покажи отдельные состояния для Screen Recording и Microphone. Микрофон требуется только `recording`; режим `answers` должен работать без microphone permission, если выбран системный источник.

## Тесты

Проверь Keychain adapter через protocol fake, отсутствие секретов в settings/db/logging, passive startup, permission routing и redaction известных форматов ключей.

## Критерии приёмки

- В репозитории и build products нет API-ключа.
- Answers не требует микрофон без необходимости.
- Пользователь всегда понимает, какой режим активен и куда идут данные.
- Diagnostic export безопасен по умолчанию.
